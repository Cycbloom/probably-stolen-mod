#### 子弹能否叠成「一小把」

不能。`GameItem` 有 `unitCount`、`SetStack(n)`、`MayStack`，`GetValue` 也按 `unitValue × unitCount` 算；但 `MayStack` 依赖可空的 `mayStackItemFunc` 委托，弹药工厂（`SmallPistolRound` / `HeavyPistolRound`）没有设置它，`MayStack` 返回 false，物品不会自动并堆。强行 `SetStack(5–8)` 会让声望用的 `GetCurrentValue`（不算 `unitCount`）与交易用的 `GetValue`（算 `unitCount`）口径不一致，因此保持单件；5% 只体现在出现概率上，不做「一小把」。

#### 枪械成色怎么表达

游戏里枪没有耐久度字段，也没有「磨损版枪」的独立 item id；成色是物品特征 `ItemFeatureList.EquipmentCondition`（New / Excellent / Good / Fair / Poor），由 `GunHelper.SetEquipmentCondition` 挂在物品上，并通过 `ItemCondition.modValue` 影响成交价：+25% / +12% / 0 / −12% / −25%。枪械工厂默认成色是 New（打印枪）或 Good（其余），所以 0.3.61 起在拾荒生成后按上表重掷成色并覆盖默认值，让废武器堆以「一般 / 破旧」为主，全新与优良合计只有约 3%–6%。

| 专精 100% + 垃圾倍率 100%（基准） | 14.10 | 21.20 | +50.4% |

#### 材料类为什么这样排（枪匠配方）

材料权重不是纯按单价反比，而是先按枪匠链条的实际消耗量定档，再用单价压高价件。枪匠的 3D 打印机（`MachinePrinter`）靠打印芯片（`ModuleDirectory` 里的 `printer_chip_*`，共 24 个）工作，每个芯片工厂通过 `SetSingleAdditionalRequiredItem(item, materialId, count)` 声明每次打印要消耗的材料；枪械组装另由 `GunFrameHelper.CanFinish` 消耗 `gun_part`。Cecil 逐条扫出来的消耗如下：

| 芯片 | 消耗 |
|---|---|
| `printer_chip_pistol` | `printer_plastic` ×2 |
| `printer_chip_pistol_double` | `printer_plastic` ×3 |
| `printer_chip_22_mag` / `_high` / `_ext` | `printer_plastic` ×2 / ×2 / ×3 |
| `printer_chip_10_mag` / `_high` / `_ext` | `scrap_metal` ×2 / ×2 / ×3 |
| `printer_chip_silencer` | `scrap_metal` ×5 |
| `printer_chip_internal_springs_improved` | `scrap_metal` ×2 |
| `printer_chip_makeshift_rds` / `_makeshift_toy_laser` | `printer_plastic` ×1 + `common_electronic` ×1 |
| `printer_chip_rds` / `printer_chip_laser_sight` | `scrap_metal` ×2 + `common_electronic` ×1 |
| `printer_chip_handmade_pistol_frame` | `metal_ingot` ×1 |
| `printer_chip_heavy_handmade_pistol_frame` | `metal_ingot` ×2 + `scrap_metal` ×1 |
| 近战芯片 `box_cutter` / `kitchen_knife` / `hatchet` | `scrap_metal` ×2 / ×3 / ×4 + `printer_plastic` ×1 |
| 近战芯片 `kitchen_cleaver` | `scrap_metal` ×5 + `printer_plastic` ×2 |
| 近战芯片 `combat_knife` / `combat_machete` | `metal_ingot` ×2 / ×3 |

结论：`printer_plastic` 与 `scrap_metal` 是绝对主力（几乎每个芯片都要），`common_electronic` 只出现在瞄具 / 消音器类，`metal_ingot` 只用在土枪框架与战斗刀 / 砍刀上。线缆（`wire`）与金属螺丝（`nuts_metal`）不出现在任何打印配方里，所以压到 5.6% / 6.2%，低于废金属与耗材一个数量级。`gun_part`（25）由枪械组装消耗，排在电子元件之前，但不再是材料里最多的一项（0.65%–3.8% 整表概率，废金属 7.61%–43.5% 类内）。

#### 贵重品池

「贵重品」是本模组自己拼的一池稀有物品，**和游戏自带的「奢侈品 / `LUXURY_ITEM`」类别不是一回事**：后者是买卖与展览用的奢侈品标签（`LuxuryItem` 特性、展柜加成等），本池只是拾荒时按概率抽取的物品清单，没有任何游戏内类别标签。

它们不进基础表：只有「贵重品出现率」大于 0 且声望达到 80 时才进入最终表，概率取该滑条（默认 3%，范围 0–30%），五个区都能掉到。池内 27 件分四类（原有 7 件保留；0.3.64 起不含超科技物品；0.3.65 起加入正品免疫宁与 4 件 100–200 的普货；0.3.66 起加入正品香烟与酵母生物反应器）：

## 2. v0.1.0 的现状

### 2.1 掉落是怎么走的

游戏侧只有一条主掉落链路：

```
ScavHelper.ScavengeDumpingGrounds()
  → ScavHelper.GetRandomScavengedItem()
    → ScavHelper.SpawnDumpingGroundLoot()
      → ItemSpawner.SpawnFromTableGroup("dumpingGroundTG")   // 普通情况
      → LootRegistry.RollGroup("dumpingGroundTG", scale)     // 有 junk_chance 事件时
```

`dumpingGroundTG` 是一个**表组**：9 张原版表（垃圾、材料、工具、日用、食品、药品、自制武器、一级模组、二级模组）各自带权重，总权重 805。`junk_chance` 事件只会抬高 `junkTable` 的权重。

v0.1.0 没有自己的物品池。它在 `RollGroup` 的 `scale` 回调里，按所选区域把其中若干张**整表乘一个系数**（入口空地作基准 1×，拆解堆侧重材料/工具，生活废料带侧重日用/食品/药品，报废终端区侧重模组/材料，量级约 2～3 倍；倍率写在代码常量与配置窗口里）。表内部的物品仍是原版等权，改不到单件。

所以旧版的实际分布是：

> 区域只决定「9 张原版表各自的份量」，同一张表内部每个物品的相对概率完全一样。

## 3. 新方案：物品级权重 + 按期望收益归一

### 3.1 物品单价取数来源

直接用游戏自己的价值字段 `GameItem.unitValue`（Cecil 逐个扫 `*Directory::InitDirectory` 里的工厂方法，取 `set_unitValue` 常量；部分日用品走 `SetValue`，同样抓取）。满盒类按内容折算：`full_water_test_strip_box` = 盒 1 + 10 条 × 3 = 31，`full_water_purification_tablet_box` = 盒 1 + 9 片 × 6 = 55。`random_*_module` 开出来的是基准模组，按 70 计。完整清单见 `work\item_values.csv`。

### 3.2 归一化方式

每个区域是一张「物品 → 相对整数权重」表，概率 = 该物品权重 ÷ 该区总权重。

设计步骤：

1. 先按区域定位手写所有**非垃圾**物品的相对权重（四区各一套，构成明显不同）；
2. 设该区非垃圾权重和 `W₀`、非垃圾价值加权和 `V₀`，垃圾单价 3，目标期望 `T = 12.2604`（原版 `dumpingGroundTG` 的期望），解垃圾权重 `w_j`：

   ```
   (V₀ + 3·w_j) / (W₀ + w_j) = T    ⇒    w_j = (V₀ − T·W₀) / (T − 3)
   ```

3. 所有权重取整，再在 `w_j ± 6` 内搜一次，取最接近 `T` 的整数解。

这样归一化的是**期望价值**而不是概率总和：垃圾权重是自由变量，用来吸收各区域物品组合的价值差，因此四个区域「总权重」各不相同（562 / 700 / 981 / 854），但单次拾荒的期望价值对齐。四区物品集合本身也不同（拆解堆不含食品与药品，生活废料带不含模组，等等），不是同一套表换倍率。

### 3.5 v0.3.5–0.3.8：区域专精度

旧版「偏好类别」是跨区通用的一个类别（材料 / 食品 / 医疗 / 工具 / 模组），对四个区同时生效，结果是把两个本来不同的区域拉向同一种出产；而且它和「地点就是主题」的设定冲突。v0.3.5 删掉该条目与下拉，改成每个区一条区域专精度滑条；v0.3.7 又把四条合成一条全局滑条 f（0–100%）——区域本身就是主题，不再逐区单独设置；v0.3.8 定名「区域专精度」。四个区共用同一个 f，但各用自己的一份特色清单，所以同一个数值在四个区出不同的东西。

生效方式（`Tuning.Build`，v0.3.6 修正后公式；v0.3.7 只把 f 的来源从四条改成一个 `specialty` 条目）：

```
对每个非垃圾物品：
  属于本区特色类别 → 权重不变
  否则             → 权重 × (1 − f)
垃圾：权重不参与这一步。

合成概率：
  垃圾概率 = 基础表垃圾占比 × 垃圾倍率        （与 f、与贵重品都无关）
  贵重品总概率 Ph 从非垃圾物品里按比例让出      （垃圾份额不被扣）
  非垃圾物品分得 (1 − 垃圾概率 − Ph) 的份额，内部按上面的权重比例分配
```

v0.3.5 的错误：把 junk 也算作「非本区物品」乘了 (1 − f)，f=100% 时垃圾被压到 0；同时贵重品份额从「全部物品」按比例让出，也扣了垃圾。垃圾应是与其余物品并列的一档权重，归一化时参与总权重，但不应被另外两个滑条改写。

各区特色类别（每区一份清单，f 是共用的）：

| 区域 | 特色类别 | 依据 |
|---|---|---|
| 入口空地 | 材料、工具、日用 | 「通用杂项：材料、工具、日用品各有一点」 |
| 拆解堆 | 材料、工具、模组 | 「材料与工具占大头，偶尔能拆出完整模组」 |
| 生活废料带 | 日用、食品、医疗 | 「日用、食品、药品为主」 |
| 报废终端区 | 模组、电子件 | 「模组与电子件的比例全场地最高」 |

选择「让位」而不是「替换成固定清单」的原因：现有四区权重表已经是按区域定位手写的，直接用 (1 − f) 缩放非特色项，f = 0 时与旧版逐项一致、f 为中间值时本区物品的相对比例不变，不需要维护第二套表；被挤出的份额在归一化时按原比例落到剩余非垃圾物品上，等价于「按比例让位给本区特色物品」。所以 f 的含义是「除垃圾外，捡到的东西里本区特色物品的占比」，设置项说明与 tooltip 就是这么写的。

同一个 f 下四区各自的结果（默认其它设置，垃圾倍率 100%）：

| 区域 | f = 0 | f = 50% | f = 75% | f = 100% | 垃圾概率（各档一致） |
|---|---:|---:|---:|---:|---:|
| 入口空地 | 12.26 | 12.13 | 12.03 | 11.90 | 48.75% |
| 拆解堆 | 12.26 | 12.37 | 12.43 | 12.49 | 51.86% |
| 生活废料带 | 12.26 | 12.20 | 12.17 | 12.13 | 43.73% |
| 报废终端区 | 12.26 | 13.34 | 14.44 | 16.72 | 68.03% |

修正后价值只小幅变化：垃圾份额被固定住，腾挪只发生在非垃圾物品内部。终端区升得最多（杂项让位给模组/电子件），入口空地与生活废料带略降（被让位掉的食品/工具/模组单价略高于本区日用品），拆解堆基本持平。垃圾概率在 f=0/50/75/100% 下完全相同，只随垃圾倍率变化（例如 80% 时 gate 为 48.75% × 0.8 = 39.00%）。预设为「默认 / 专精拉满 / 赌贵重品」，其中「专精拉满」把这条区域专精度设为 100%。

### 5.3 第三方 mod 兼容（0.3.77，不涉及掉落权重）

两处兼容各自独立，都不读写存档、不改掉落表与概率，因此本文上面的权重与 EV 表格全部不变；两个第三方 mod 都不安装时走原路径。

**背包挂钩（`backpack_wall_slot_mod`）**

- 对方的实现：`EmporiumEntry.TransferAfterhourToInv` 前缀置「正在处理离场口袋」标志，`EmporiumEntry.TryAddToPlayerInv` 前缀（Priority 800）在该标志为真、物品是背包、`BackpackHookInnerSlot` 为空时把包 `TryAccept` 到挂钩并跳过原版。「返回时自动挂包」是对方已实现的行为。
- 本模组的改法：`ScavHelperService.CarryBack` 在装了它时跳过 `afterhourPocketSlotInvBackpack`，只搬右手 / 左手 / 地面，包留在口袋里由原版离场流程交给对方挂墙，省下店内一格。
- 判定只用 `ModHelper.IsModRunning("backpack_wall_slot_mod")`，无反射、不引用对方类型；`<Capabilities />` 仍为空。
- 挂钩被占或功能关闭时对方不接手，原版 `TryAddToPlayerInv` 三级尝试（后场 → 柜台 → 展示柜）照常放包，全满则留在原口袋槽、不销毁。
- 帮手搬运与地面溢出提示统计的都是 `afterhourInventory`，挂在墙上的包不在其中，不重复占位。

**势力声望面板重制（`cirno9.reputation_interface_remake`）**

- 差异定位：对方整套替换渲染——`ReputationUIManager.OpenUI` 前缀 / 后缀取原生 `layout`，`BoardData.Collect` 遍历其中 `ReputationElement` 生成 `BoardEntry`，隐藏原生 layout 后用自己的 `BoardRow` 显示。我们插入的行仍在 layout 里并被收集；小数丢失的原因是 `BoardData.Fill` 在 `entry.Rep != null` 时直读 `StoreReputation.GetReputationExact().ToString("+0.00;-0.00;0.00")`，而合成行当时写的是整数点数。
- 本模组的改法：`Reputation.BuildEntry` 改 `SetReputation(Reputation.ExactPoints)`（累计价值 / 100，未取整）。原版面板的 `ApplyRow` 仍覆盖为 `x.xx/200`，显示不变；重制面板读到两位小数。
- 档位门槛、绿条高度、图标解锁仍走 `GetReputation()`（`(int)amount` 截断），整数判断不受影响；悬停文案未改。
- 已知差异（改动前即存在）：重制面板的状态文字用原生 `GetReputationStatus(int)` 通用档名，数字统一 `+0.00` 且不带 `/200`，对所有派系一致。

### 5.5 声望按难度缩放（0.3.79，不涉及掉落权重）

倍率来源：`Difficulty.Rules.reputationGainMultiplier`。它在 `Difficulty.Vanilla()` 里随四档难度定义，原生 `StoreReputation.ModReputation` 用它乘正声望增量（负增量另用 `reputationLossMultiplier`）。

| 档位 id | 名称 | 倍率 | 1 点声望需要 |
|---|---|---:|---:|
| `cozy` | Price Gouge | 1.5 | 约 66.7 价值 |
| `normal` | Mark Up | 1.0 | 100 价值 |
| `hard` | Thin Margins | 0.75 | 约 133.3 价值 |
| `challenge` | Red Ink（赤字连连） | 0.5 | 200 价值 |

- 取值：`PlayerStore.HasInstance`（挡住无存档时 `PlayerStore.Instance` 的副作用）→ `Difficulty.Current` → `Difficulty.Rules`；取不到或值非正时退回 1.0。
- 作用位置：`Reputation.Add` 里乘在**本次新增的累计价值**上（`round(value × multiplier)`），再写回 `rep_total_value`。不乘在点数增量上，因为存档存的是累计价值：乘在新增价值上等价于按难度改「每点成本」，同时保证已累计的旧值（旧档、换难度前后）不被追溯重算。
- 初始声望：`ScavengerStart` 用同一个倍率乘 20 点基准（30 / 20 / 15 / 10）。
- 调试写点（`debug_points` → `Reputation.SetPoints`）不乘倍率。
- 不改掉落表、物品单价、存档键结构；`<Capabilities />` 仍为空。
